# Worker guard

Prefix-matched deny rules such as `Bash(herdr server stop:*)` are defeated by an env prefix (`HOME=x herdr server stop`, incident M86). Every worker role (pm, coder, qa, reviewer, judge, cleaner) therefore also has a `PreToolUse` hook on the Bash tool in `roles/settings/<role>.json.in`: `python3 <live home>/roles/hooks/worker-guard.py`. Boss, director and lead run the hook in HQ mode (`--hq`, see PRIV below). The hook reads the tool-call JSON on stdin and exits 2 with a reason on stderr to block. Settings apply only to newly spawned workers.

Rule (Python stdlib, `shlex`, fail closed: an unparseable command, bad JSON or an internal error blocks):

- A command word is the first word of a simple command, after env assignments, redirections and shell keywords. Commands are split on `; & && || | ( ) { }` and newlines, and also searched inside `$( )`, backticks, `sh/bash/zsh -c` payloads (nested), `eval`, heredocs fed to a shell, and shell scripts read from disk (`bash f`, `source f`, `./f`).
- Blocked: a command word `herdr`, or any path whose basename is `herdr` (`/usr/bin/herdr`, `~/.local/bin/herdr`, `./herdr`), except a path under `tests/stubs/` (the unittest stubs). Also blocked: a dynamic command word (`$H`, `${H}`, `her*`, `{herdr,x}`) because it may expand to herdr.
- Wrappers (`env`, `sudo`, `exec`, `command`, `nohup`, `timeout`, `xargs`, `busybox`, `ssh`, `watch`, `find -exec`, ...) are checked at every later position, so `sudo -u x env A=1 herdr` is caught without modelling each option. `alias`/`ln`/`cp` of herdr and `python -c` code that names herdr are blocked too. `pkill`, `killall` and `kill` follow the kill rule below.
- `herdr` as a plain argument stays allowed: `grep herdr README.md`, `echo herdr`, `cat tests/stubs/herdr`. A wrapper with herdr as a later word (`timeout 5 grep herdr f`) is a known false positive.
- `systemctl` with enable/start/stop/restart/reload/daemon-reload/disable/kill/mask/unmask/link (and similar) is blocked when the unit is `factory-*`, `herdr*`, a glob, or absent (`daemon-reload`). `status`, `cat`, `show`, `is-active`, `list-units` and `systemd-analyze --user verify` stay allowed.
- `bin/factory`'s own herdr calls are untouched: the hook only sees the agent's Bash commands.
- **Claude (G-006 B2, lesson M347):** only `factory spawn` starts Claude. A command word `claude`, or any path whose basename is `claude` (`/usr/bin/claude`, `~/.local/bin/claude`, `./claude`), is blocked at every position the parser checks: after env assignments, behind the wrappers, inside `$( )`/backticks, `sh/bash/zsh -c` payloads, `eval`, shell heredocs and scripts read from disk. A dynamic command word or `$(which claude)` is blocked too. `npx`/`bunx`/`pnpm dlx`/`npm exec` with an argument containing `@anthropic-ai/claude-code`, and `node` (or bun/deno) running a `claude-code/.../*.js` file, are blocked. The stderr reason is `only factory spawn starts Claude (lesson M347); ask your lead`. The `tests/stubs/` exemption does not apply (there is no claude stub). `claude` as a plain argument stays allowed (`grep -rn claude README.md`, `echo claude`, `cat ~/.claude/settings.json`, `git commit -m "mention claude -p"`). `alias c=claude` is blocked like the herdr form, and an alias or assignment VALUE that is a command line (`alias c="claude -p"`, `function c { claude; }`) is re-parsed as a command and judged like a top-level one, also inside scripts read from disk. A wrapper with claude as a later word (`xargs grep claude`, `find . -exec grep claude {} \;`, `timeout 60 grep claude f`, `nohup grep claude f`) is a known false positive, the same as for herdr. A dynamic command word (`$X`, `$(...)`) is blocked with a message naming both rules.
- **Persistent roles:** boss, director and lead have no guard hook, only `Bash(claude:*)` in `permissions.deny` of `roles/settings/{boss,director,lead}.json.in` (applies after a relaunch). Known limit: a prefix deny rule is defeated by an env prefix (`FOO=1 claude -p x`), so those roles can still bypass it; the A6 tick audit (T-0064) detects a claude process started under an agent after the fact. `bin/factory` starts Claude through `herdr agent start`, not through an agent's Bash tool, so the deny rule does not touch the factory's own launches.

Factory unit commands (T-0031): the hook is started as `worker-guard.py --role <role>` (no flag means a non-cleaner worker) and also blocks a command word `factory` (or a path with basename `factory`, including `python3 <path>/factory`) whose subcommand is `up`, `tick`, `relaunch`, `spawn` or `clean`, unless the same simple command sets `FACTORY_HOME=<path>` to a path that is not the live home (a temp home for QA), or the subcommand is `clean` and the role is `cleaner`. Behind the hook, `bin/factory` itself refuses those commands, `team new`, `team close` and a message to the on-demand staff-engineer (which would spawn it in-process) for any worker (found by process ancestry, `FACTORY_ROLE`, the DB role or the pane id; the claimed `FACTORY_AGENT` role does not matter), before any DB write; `spawn()` repeats the refusal. `herdr()` default-denies every verb outside a read-only allowlist for workers (event `herdr-denied`, exit 3). The one exemption, `worker_stub_exempt()`, needs BOTH a `herdr` under `tests/stubs/` first on PATH AND a `FACTORY_HOME` that is not the live home; either alone is refused. A worker in a non-live `FACTORY_HOME` that has no configured `herdr_socket`, or no readable DB, gets a dead socket path instead of the live one. The hook also carries an identity belt (E1, below): `setsid`, `disown` with factory, `unset`/`env -u` of `FACTORY_ROLE`/`HERDR_PANE_ID`, `env -i` with factory, and a `FACTORY_AGENT=<other>` assignment are blocked, except `FACTORY_AGENT=<own name>` and any assignment next to a temp `FACTORY_HOME` (a static path or `$(mktemp [-d] [-p dir])` outside `~/factory`).

Broad factory reads (G-005 item 1): for every worker role the hook also blocks a command word `factory` (also `python3 <path>/factory`, wrappers, `$( )`, `bash -c`) with the subcommand `res`, `agents`, `scorecard`, `digest`, `config`, `goal list`, `lesson list`, `task list`, `task ready`, `team list`, `project list`, or `goal show <id>` for any id but the worker's own. The block message names the command and says to use `task show` / `goal show <own goal>`. The same simple command may set a temp `FACTORY_HOME` (the `temp_home` rule, or a static path / `$(mktemp -d)` outside `~/factory`) to escape; `export FACTORY_HOME=...; factory res` and `cd /tmp && factory res` stay blocked. The own goal is `agents.goal_id` for `$FACTORY_AGENT` in `<$FACTORY_HOME or the live home>/db/factory.db (legacy: factory.db)`, opened read-only on every call; if `FACTORY_AGENT` is unset, the row or goal is missing or the DB is unreadable, `goal show` is blocked (other commands are unaffected). Exempt: `--role staff-engineer` (reads factory state to advise) and `factory agents` for `--role cleaner`. `whoami`, `inbox`, `msg`, `done`, `verdict`, `report`, `plan`, `goal audit` (the pm's own write path; `goal signoff` is refused for workers by the CLI itself, `refuse_worker`), `task show|add|update|note` stay allowed. Options fail closed: argparse flags are not modelled (`--goal X` takes a value, `--all` does not), so any option token (`-x`, `--x`, `--x=v`, `--`) before the action word of `goal|task|team|project`, or before the id of `goal show`, blocks the command (`factory task --goal G-005 list`, `factory goal --goal G-005 show G-005`); options after the action/id are unchanged. To see the full view of your own goal (G-014: workers get a compact `goal show`/`task show` by default), put `--full` after the id: `factory goal show G-005 --full` is allowed, `factory goal show --full G-005` is blocked (option before the id). A wrapper argument with whitespace is re-parsed (the known false positive above), so `timeout 60 grep "factory res" README.md` is blocked too.

Privilege escalation, rule PRIV (T-0057, owner M803): the agent uid keeps passwordless sudo, but no agent may use it. Every role's `permissions.deny` lists `Bash(sudo:*)`, `Bash(su:*)`, `Bash(doas:*)`, `Bash(pkexec:*)` and `Bash(docker:*)`, and the hook blocks a command word `sudo`, `su`, `doas`, `pkexec` or `docker` (or a path with that basename: `/usr/bin/sudo`, `./sudo`, `"$(command -v sudo)"`) with the reason ``privilege escalation (`<word>`) is not allowed for factory agents (owner M803)``. It follows the same forms as the herdr rule: env-assignment prefixes, the wrappers `env`, `exec`, `nohup`, `timeout`, `xargs`, `command`, `nice`, `ionice`, `setsid`, `stdbuf`, `watch`, `busybox` (their options are modelled, so `timeout 5 grep sudo f` stays allowed) and `find -exec`, `sh|bash|zsh -c` (nested), `eval`, scripts read from disk, `$( )` and backticks, chains, subshells, brace groups, backslash continuations, and quoting tricks the shell normalises (`su''do`, `s\udo`). Interpreter heredocs and inline code (`python3 -c`, `perl -e`, also behind option values such as `python3 -W ignore -c`) are blocked when they name one of the words. The word as data stays allowed: `grep sudo f`, `git commit -m "block sudo"`, `echo su`, `cat docs/sudo.md`, `ls /usr/bin/sudo`, `which sudo`, `command -v sudo`, heredoc bodies fed to `cat` or `factory`, and `su` as a substring (`sum`, `git status -su`). Known false positive: interpreter code that merely mentions `sudo` or `docker` as a word. Also followed (reviewer B3/B4): in worker mode a glob command word that may expand to a PRIV word (`/usr/bin/s?do`, `sud[o]`) is blocked like a glob that may expand to herdr (not in HQ mode); `git -c alias.x='!sudo id' x`, `git -c core.pager=...` and `git config` of a command-valued key; `sed` `e` commands and `s///e`; `awk` `system()` and pipes to a quoted command; `trap '...' SIG`; `time -p CMD`; `function f { ...; }`. A `$( )` or backtick inside single quotes is data and never analysed. Interpreter options are modelled per interpreter (`python3 -I`/`-E`/`-d`/`-x` are plain flags, `-W`/`-X` take a value, attached or separate); an option the model does not know makes the script position unknown and the checks fail closed (every later word is a candidate: `python3 -Z bin/factory tick` is blocked).

PRIV gaps in HQ mode only (worker mode blocks them; accepted so HQ keeps zero false positives): `echo 'sudo id' | bash`, `bash < <(echo sudo id)`, `source <(echo sudo id)`, `$'sudo' id`. `runuser`, `sg` and `newgrp` are wrappers (their later words are checked) but not PRIV words themselves. The cleaner's other ref mutations (`git branch -M/-f`, `git update-ref -d`) are not covered; follow-up.

HQ wiring: `roles/settings/boss.json.in`, `director.json.in` and `lead.json.in` carry a `PreToolUse` Bash hook `python3 <live home>/roles/hooks/worker-guard.py --hq`. HQ mode runs the PRIV rule and the mutating-unit rule (last section), with the same parsing. None of the herdr rules (R1/R2/R3, direct herdr, systemctl factory-*/herdr*), the factory-unit and broad-read rules or the identity/scrub checks apply, because HQ drives herdr and the units through `factory`. A dynamic command word (`$X`, `${X}`) is not blocked, except a `$( )` command word that names one of the five words, and a command the parser cannot read is allowed (no false positives). Worker roles keep `--role <role>` and every rule above, with PRIV added; the PRIV pass runs first in worker mode too. HQ settings only take effect after `factory relaunch` of the HQ pane (workers get them on spawn).

Cleaner branch deletion (T-0057, director M1112): `roles/settings/cleaner.json.in` allows `Bash(git branch -D factory/*)` and `Bash(git push origin --delete factory/*)`; the broad denies `git branch -D:*`, `git push origin --delete:*` and `git push:*` are gone, because a Claude Code deny beats an allow and `git push:*` would still catch the delete. The hook enforces the scope instead: `git branch -d|-D|--delete` and `git push <remote> --delete|-d|:<ref>` are blocked for every worker role, except `--role cleaner` when every target matches `^factory/[A-Za-z0-9._/-]+$` (no `..`, no glob). `main`, `state`, `:main`, other prefixes, mixed lists and globs are refused, and any other `git push` by the cleaner is refused. The existing `git push origin main`, `HEAD:main`, `--force` and `-f` denies stay.

Kill rule (T-0102, director M1938 after the G-008 incident where `pkill -f "unittest discover"` killed every agent's suite). Worker mode only; HQ mode is unaffected. `pkill` and `killall` are blocked as command words. `kill` is blocked unless every target is the worker's own background job: `%<job>`, `$!` or `${!}` (`kill %1`, `kill -TERM $!`, `kill -s TERM %1`). A pid, `0`, `-1`, a negative pid or process group (`kill -- -123`, `kill -9 -1`, `kill -s KILL -1`), `$VAR`, `$(pgrep x)` and a `kill` with no target (`xargs kill`) are blocked, as is the same through the wrappers, `find -exec`, `sh -c` and chains. `kill -l` is allowed. The words as text stay allowed: `grep pkill README`, `git commit -m "no pkill"`, `ps aux | grep unittest`, a `factory report` body that mentions killall. Known false positive: a wrapper with `kill` as a later word (`timeout 5 grep kill f`), the same as for herdr.

Parsing alone cannot close every spelling, so the guard is three layers deep:

1. **Parser** (above). Also blocks a command word that comes from `$( )` or backticks, `sh <<< "..."` here-strings and `bash <(...)` process substitution, `sh -c` with its payload on stdin (`xargs -0 sh -c`), an `xargs -I{}` placeholder used as the command word, `eval` of an expansion, herdr named in `awk`/`gawk`/`vim`/`sed 'e'` program text or `git -c`/`git config` values, and `systemctl isolate`.
2. **Raw-text backstop**, run before parsing and independent of it. Stub paths (`tests/stubs/herdr ...`) are exempt.
   - **R1 (placeholder exec):** a `herdr` word followed later on the same line (after joining `\`-continued lines, any tokens between) by `server <word>`, or by `agent|pane|tab|workspace|worktree` and `start|stop|kill|close|prompt|split|new|run|send|create|move|swap|remove|rename`, is blocked, but only when an exec-capable launcher is also in a command position on that line (`find -exec/-execdir/-ok`, `xargs`, `env`, `sudo`, `nohup`, `timeout`, `command`, `exec`, `nice`, `ionice`, `setsid`, `stdbuf`, or `sh|bash|zsh|dash -c`). Without a launcher the phrase is plain text and allowed.
   - **R2 (socket re-target):** any text that sets or exports `HERDR_SOCKET_PATH` or `HERDR_SESSION`, or contains `herdr.sock` or `.config/herdr`, is blocked. Quoted `herdr.sock` / `.config/herdr` inside a `git`, `gh`, `grep`, `rg`, `cat`, `less`, `echo`, `printf` or `factory` command is data and allowed. Unsetting `HERDR_SOCKET_PATH` (`unset`, `env -u`, `env -i`) is blocked only when the same text also has a `herdr` word, so `env -i PATH=... python3 -m unittest` stays allowed.
   - **R3 (binary copy):** `cat|dd|cp|install|rsync|tee|ln|mv|base64|xxd|head|tail` on the real herdr binary (basename `herdr` outside `tests/stubs/`, or `$HERDR_BIN_PATH`, also `dd if=` and `< path` redirections) is blocked. Reading the stub is allowed.

   Plain-text mentions (`grep 'herdr server stop' tests/`, `git commit -m '...'`, `gh pr comment --body '...'`, `factory msg ... '...'`) are allowed.
3. **Socket isolation.** `bin/factory`'s `herdr()` always passes `HERDR_SOCKET_PATH=<config herdr_socket>` (default `~/.config/herdr/herdr.sock`, see `factory config`) to the herdr subprocess, whatever the caller's env holds, so the tick, `factory spawn/res/done` and the systemd units keep working. The six worker `roles/settings/*.json.in` set `HERDR_SOCKET_PATH` to `/proc/nonexistent/worker-no-herdr.sock`, a path nothing can create, so any herdr a worker shell still manages to run, however spelled, cannot reach the live server. Boss, director and lead keep the real socket. (Confirmed from the herdr binary's strings: client and server both read `HERDR_SOCKET_PATH`; herdr was not run.)

`HERDR_ENV` and the other `HERDR_*` pane variables stay, because identity detection uses them.

Known gaps (documented and accepted; tracked in T-0021). The guard is aimed at accidental misuse by a well-meaning agent, not at an adversary; it is not a sandbox, and the process-tree, env and hook checks can all be defeated by a determined worker. Layer 3 stops any herdr run from a worker shell unless the socket is re-pointed in the same command, and R2 blocks that re-pointing. What parsing cannot close:

- `find -exec {} ...` and `xargs -I{} {} ...` placeholder forms, when R1 (launcher-gated) does not catch them.
- Other command-running sinks (reviewer B1): `trap '...' EXIT`, `at` / `batch`, interpreter code on stdin or `<<<`, `make -f -`, `PROMPT_COMMAND`, `BASH_ENV`, `GIT_PAGER`, `GIT_SSH_COMMAND`, `LESSOPEN`.
- Option tokens between `herdr` and its verb, and backslash continuations that are not joined (reviewer B2).
- Interpreter string-building (`'her'+'dr'`), `python3 x.py` where the script spawns herdr itself, a `bash < file` whose file holds the command, a script written and run in the same command, a symlink alias to the binary (R3 blocks `ln` on it), `pgrep`-based kills that never write the word, and `loginctl terminate-user`.
- Claude rule (T-0067): `export`/`declare` of a claude value that is never executed in the same command (`export CMD="claude -p"` alone; `$CMD x` is caught), and interpreters that exec it (`python3 -c 'os.execvp("claude", ...)'`, node, perl). Alias/assignment values are re-parsed as a command line, so quoting, `;`/`&&`/`|` and backslashes in them are caught; new exotic forms are left to the T-0064 process audit.
- **E1 (open, belt only):** a worker can re-parent out of its claude process tree (`setsid -f`), scrub `FACTORY_ROLE` and `HERDR_PANE_ID`, and claim `FACTORY_AGENT=director`; that defeats all four detection signals. The hook now blocks those spellings (see above) but a script that does it, or a new spelling, still works. The real fix is a design decision pending with the owner.
- **E2 (closed for the live home):** a worker-made wrapper under a `*/tests/stubs/` directory used to hand the live socket over. The exemption now also needs a non-live `FACTORY_HOME` (`worker_stub_exempt()`). What remains is a temp home plus a wrapper or a separately configured socket path, which is the documented "a script runs herdr itself" gap above. A configured `herdr_socket` that expands (for the real user, not the env HOME) to the live default is replaced by the dead socket for a worker in a non-live home.

Known false positive (C9): any command text containing a dollar-paren sequence is blocked, even inside quotes (a PR body with command substitution text). Pass long PR or commit text with `--body-file <file>` / `git commit -F <file>`.

## Mutating systemd commands (T-0102 part D, owner M2108)

No agent manages units: the owner installs them, and `factory up` runs from systemd, not via it.

- HQ mode (`--hq`) refuses `systemctl` (with or without `--user`) with a mutating verb: start, stop, restart, reload, try-restart, reload-or-restart, enable, disable, reenable, daemon-reload, daemon-reexec, edit, mask, unmask, set-property, revert, link, preset, kill, reset-failed, isolate, set-environment, unset-environment, import-environment. The read-only verbs (status, is-active, is-enabled, is-failed, list-units, list-unit-files, list-timers, cat, show, help) and bare `systemctl --user` stay allowed.
- `systemd-run` in any form is refused in HQ and worker mode.
- Both go through every form the PRIV rule analyses: env prefix, wrappers, `bash -c`, `$( )`, unquoted backticks, chains, subshells, `find -exec`. Quoted text (`grep "systemctl --user start" f`, a commit message) is data.
- Worker mode keeps its own rule (mutating verbs on factory-*, a glob or no unit).
- Block message: `mutating systemctl/systemd-run is not allowed for factory agents; the owner manages units (M2108)`.

Heredoc delimiters (T-0178): `heredoc_delim` resolves the word after `<<` / `<<-` the way bash does: `'..'` is literal, `".."` drops a backslash before `$`, a backtick, `"` or `\`, an unquoted backslash is dropped, and `<<-` strips leading tabs (not spaces) from body lines. A body line ends the heredoc only when it equals the resolved delimiter exactly. A form it cannot resolve with certainty (`$'..'` or `$".."`, a backslash-newline or newline in the word, an unterminated quote, a missing word) with more lines after it raises `HeredocBlock` (rc 2 in worker and HQ mode) instead of being scanned as code. `tests/test_worker_guard_heredoc.py` compares the hook with real bash on a corpus of delimiter forms, using a marker file in a temp dir.

Heredoc parsing (T-0199, T-0587): `<<` inside `$(( ))` or `(( ))` is a shift operator, never a heredoc. `let` is not special: bash parses `<<` after `let` as a heredoc (`let x=1<<EOF` starts one), so the guard does too. A `((` or `$((` counts as arithmetic only when its parens close as `))`; otherwise bash re-parses them as nested groups and a `<<` there is a heredoc. A `<<` outside arithmetic whose delimiter the guard cannot resolve, with more lines after it, raises `HeredocBlock` in worker and HQ mode (body never scanned as code with the error swallowed). Inside `$( )` a body line `DELIM)` (or `DELIM )`) ends the body and the `)` closes the substitution. An unquoted heredoc body is expanded by bash, so its `$( )` and backtick contents are checked as shell. Bash decides where a `$( )` ends with its full grammar, so the guard does not guess: `scan_comsub` is an ALLOWLIST. It accepts only word characters (`A-Za-z0-9_./:=+%@,~*?^!-`), space, tab, newline, `; | & [ ]`, a single `<` or `>` (also `>>`) not followed by `<` or `(`, a `#` only in the middle of a word, balanced `( )`, `'...'`, `"..."` holding only word characters, space, `'`, `(`, `)`, `$NAME` and `${NAME}`, `$NAME`, `$1`-`$9`, `$?`, `$$`, `$!`, `$#`, `$@`, `$*`, `${NAME}`, and nested `$( )` / `$(( ))` under the same rules. Everything else is unknown: a backslash, a backtick, `$'`, `$"`, `${` with anything but a plain name (`${x/)/y}`, `${x#)}`, `${x:-)}`), `{` `}`, `<<` (a heredoc or `1<<2` inside the body), `<(`, `>(`, a bare `$`, a `#` that is not mid-word, the words `case` and `esac`, and an unterminated `$( )`. An unknown shape raises `HeredocBlock` and exits 2 in worker and HQ mode (the one parse-based block in HQ mode; narrow: unquoted heredoc plus an unmodelled `$( )`) with the message `unquoted heredoc body has a $( ) the guard cannot parse; quote the delimiter (<<'EOF') or compute the value before the heredoc`. Workaround: quote the delimiter (`<<'EOF'`, the body is data and is not scanned) or compute the value before the heredoc. An unbalanced backtick in an unquoted body raises `HeredocBlock` (rc 2 in worker and HQ mode; message `unquoted heredoc body has an unbalanced backtick the guard cannot parse`), never a swallowed parse Block. `tests/test_worker_guard_heredoc.py` and `ci/guard_corpus.json` hold each shape for both modes.

Known gap (pre-existing on main, not fixed in T-0587): a `<<-` heredoc whose delimiter contains a backslash, opened inside a `$( )` that starts with a subshell, e.g. `$((echo a); <<-E\OF` followed by body lines, a terminator and a privileged line, is not blocked in either mode. Also pre-existing: a triple-paren opener `(((x=1<<2)); cat <<EOF)` (subshell inside a subshell, found by the T-0646 fuzz) has its `<<` read as arithmetic and is not blocked in either mode.

Heredoc body scanning (T-0178 attempt 3): in an unquoted body bash joins backslash-newline before comparing a line with the terminator, so the hook does too (`EO\` + `F` ends a `<<EOF` body). Every raw line consumed by that join is scanned as one block with its newlines intact, and the joined line is scanned as well when it differs from the first raw line. Bodies fed to a shell go back through `preprocess`, which joins continuations itself, so the raw block covers them. Interpreter bodies are only searched with the code checks, so only the joined line catches a word split across a continuation line. A quoted delimiter never joins. Known gap, not fixed here: with `<<-` bash strips leading tabs from each raw line before joining, while the hook strips them only from the joined line, so the terminator can be mis-detected; the body side stays fail-closed because of the raw append.

## Shared-checkout git guard (T-0068)

A worker never changes the shared checkout `~/factory` (branch `main`), where the tick commits and pushes state every minute. For a command word `git` (also behind wrappers, `sh -c`, `$( )`), the hook works out the effective directory: the hook's cwd, moved by a preceding `cd`/`pushd`, then `git -C <dir>` (last wins, relative to the current dir), `--work-tree` and `--git-dir` (also as `GIT_WORK_TREE`/`GIT_DIR` assignments, e.g. `env GIT_DIR=... git ...`). A `cd` inside `sh -c '...'` does not move the caller; a `cd` in a plain `( ... )` subshell does (known false positive). A dynamic directory (`$VAR`, `$( )`, a glob, `cd -`, `popd`) counts as the shared checkout.
- `.git` test, no git run: walk up from `realpath(dir)` to the first ancestor containing `.git`. A `.git` FILE is a linked worktree (every task worktree under `~/factory/worktrees/`), never shared, so there is no prefix match on the live home. A `.git` DIRECTORY is a main checkout, shared when its realpath is the live home. A `--git-dir` inside `<home>/.git` (not under `.git/worktrees/`) is shared too.
- In the shared checkout, mutating subcommands are blocked for every worker role (pm, coder, qa, reviewer, judge, cleaner, staff-engineer): commit, push, merge, rebase, reset, checkout, switch, restore, stash, clean, cherry-pick, revert, am, apply, pull, rm, mv, add, tag, update-ref, gc, prune, filter-branch, `branch` with a flag other than the list/verbose ones or with a new-branch name, `worktree` add/remove/move/prune/lock/unlock/repair, `config` with a value or `--unset/--add/--edit`, `remote` add/remove/set-url/..., `notes` add/remove, and any unknown subcommand (fail closed). Boss, director and lead (`--hq`) are not covered.
- Read-only subcommands stay allowed everywhere: status, log, diff, show, rev-parse, ls-files, ls-tree, cat-file, blame, grep, describe, fetch (all worktrees share one `.git`, so blocking it protects nothing), shortlog, rev-list, show-ref, merge-base, ls-remote, for-each-ref, diff-tree, name-rev, `branch` with no args or `--list/-a/-r/-v`, `worktree list`, `remote -v`, `config --get/--list`, `notes list/show`.
- Cleaner exemption, shared checkout only: `git worktree remove <path>` (not with `-f/--force`), `git worktree prune` and lowercase `git branch -d <name>`. The branch scope of T-0057 (`factory/*` only) still applies on top. Everything else stays blocked for the cleaner.
- Block reason: the command plus "workers never change the shared checkout ~/factory (branch main); work in your own worktree (your cwd under ~/factory/worktrees/)".
- Tests set `WORKER_GUARD_LIVE_HOME=<fixture home>` in the hook's environment to replace the live home for this rule; it is read from the hook process, which a command run by the worker cannot change. Settings apply only to newly spawned workers; rollback = revert the PR.

Source: shared-checkout git guard, idea from gAmUssA/coding-policy @7a25169 (declares MIT, no LICENSE file); our own code.

## Repo git config writes (T-0226)

Every task worktree shares `.git/config` with the live checkout `~/factory`, so a worker could plant `filter.<x>.smudge`, `diff.<x>.textconv`, `core.hooksPath`, `core.fsmonitor`, `core.sshCommand` or `remote.<x>.uploadpack` there and have it run as the next agent's plain `git status`. The hook therefore refuses repo-config writes by **allow-list, not by key**, for every worker role and from any cwd:

- **Refused:** every `git config` write form (`<key> <value>`, `--add`, `--unset`, `--unset-all`, `--replace-all`, `--rename-section`, `--remove-section`, `--edit`/`-e`, `--local`, `--worktree`, `set`/`unset`/`edit`) and `git remote add|set-url|rename|remove|rm|set-head|set-branches`. Also via `git -C <dir>`, `--git-dir`, `--work-tree`, after `cd X ;`/`cd X &&`, behind `git -c alias.x=...`, `env`, `sh -c`. A `GIT_DIR=`, `GIT_WORK_TREE=` or `GIT_CONFIG*=` assignment, or a cwd known only at run time, is undecidable and refused.
- **Allowed:** reads (`--get*`, `--list`/`-l`, `get`, `list`, `git remote -v|show|get-url`); `git config --file <file>` when the file resolves inside the worker's own scratchpad; and any write whose repository is a clone with its own `.git` (or a bare repo) inside the scratchpad. A linked worktree is never allowed, even inside the scratchpad, because it shares the origin's config.
- **No key allow-list.** No role file, plugin, doc or `bin/factory` path asks a worker to write repo config, so the key allow-list is empty. `bin/factory`'s own config handling goes through `git_run`/`git_config_refusal` (see `docs/git-hardening.md`) and does not run `git config` from a worker.
- **Edit/Write and Bash writes** (`>`, `>>`, `tee`, `cp`, `mv`, `ln`, `install`, `sed -i`, `dd of=`) to `<x>/.git/config*`, `<x>/.git/worktrees/<n>/config*`, `<x>/.git/info/attributes`, or `config`, `config.worktree`, `info/attributes` of a bare repo are refused, unless the path is inside the scratchpad. Reads (`cat`, `grep`, `cp` from it) stay allowed.

This is accident prevention (defense in depth), not a security boundary: a text check cannot see every spelling (see "Known gaps" in `docs/git-hardening.md`). Tests: `tests/test_worker_guard_repocfg.py`; corpus entries in `ci/guard_corpus.json`.

## The live factory home (T-0212)

Several guards ask "is this the live factory home?" (the evaluator tripwire, the worker test-stub exemption, the live-socket check, `protocol.file.allow`, the hook's own broad-read and `FACTORY_HOME` rules). `bin/factory` and `roles/hooks/worker-guard.py` answer it with the same rule. The hook may not import `bin/factory`, so it carries a small duplicate `derive_live_homes()` (keep the two identical).

**Derivation.** `pw_dir = pwd.getpwuid(os.getuid()).pw_dir`. `LIVE_HOMES` is `{realpath(<pw_dir>/factory)}` plus the single path in `<pw_dir>/.config/factory/live_home`, if that file is valid. `<pw_dir>/factory` is always live. `LIVE_HOME` (a string) is the primary: the file value when valid, else `<pw_dir>/factory`. Every check is `<candidate>.resolve() in LIVE_HOMES`.

**Why env is not trusted.** A worker can set `HOME`, `XDG_CONFIG_HOME` or any other variable in its own command, and `HOME` is not one of the identity variables the hook watches. So neither file nor base directory is ever taken from the environment. The location of the running `bin/factory` is not used either: a worker running `worktree/bin/factory` would make its own worktree "live". There is no env-var test seam; tests patch `pwd.getpwuid` in-process.

**The file only adds.** `live_home` is ignored unless it is a regular file (not a symlink) in a directory that is not a symlink, owned by the current uid, not group- or other-writable, and holding exactly one absolute path. Because it can only add a live home and never remove `<pw_dir>/factory`, forging or deleting it is at worst a denial of service (a legitimate temp home gets refused), never an escape. The rendered role settings follow `LIVE_HOME`, so `bin/factory` pins it (T-0213): for a live `FACTORY_HOME`, `settings_tokens()` dies with `live_home <X> != running checkout <Y>: refusing to render settings` and writes nothing unless `realpath(LIVE_HOME) == the checkout bin/factory runs from == FACTORY_HOME`. There is no fallback to `<pw_dir>/factory`. The owner writes it with `factory init --live-home <abs path>`: it refuses when `FACTORY_ROLE` is set, never overwrites a different value, is a no-op for the same value, and without the flag `init` never touches the file.

**Union with the hook's checkout.** Inside the hook, the live homes are `LIVE_HOMES` plus the root of the checkout the hook file itself lives in (`HOOK_REAL`). That one is trusted because the settings name the hook by absolute path; the hook command must stay an absolute live-checkout path (T-0213).

**Bash write detector (best-effort).** For every worker role the hook refuses Bash commands that write `<pw_dir>/.config/factory` (the directory or `live_home`) and `<live>/run/settings` (the rendered role settings): redirects (also after `cd` into it), `tee`, `touch`, `mkdir`, `cp`/`install`/`rsync`/`dd` with it as destination, `mv`, `rm` (also of a parent such as `~/.config`), `ln`, `truncate`, `chmod`, `sed -i`, `awk`, interpreter one-liners that name `.config/factory`, `live_home` or `run/settings` (also split by literal string concatenation, e.g. `'live_'+'home'`; other string assembly such as `.format` or `os.path.join` is not caught, and an interpreter that merely reads `run/settings` is blocked too), and `factory init --live-home` (any argparse prefix of the flag). `~` and `$HOME` are read as the passwd home. Reads (`cat`, `grep`, `ls`) stay allowed. This is incomplete by nature: code assembled at run time (`Path.home() / ".config"`), a script file that writes there, or a `cd` into a directory only known at run time are not caught. The real guarantee is the file-only-adds rule above, plus the Edit/Write deny rules for `<pw_dir>/.config/factory/**` in the settings templates (T-0213). Known best-effort gaps, not caught: a parent-dir destination, `~user`, globs, `find -delete`/`-exec`, `xargs`, `tar -C`, `unzip -d`, `curl -o`, `wget -O`, `git clone`, and `cd "$HOME/..."`. The SECURITY.md known limits (T-0216) list this.

## Public text (G-021)

The hook is the one place every agent-written public text passes before it leaves the box, so it also guards what git and gh write. Both worker mode (`--role <r>`) and `--hq` mode run it; the existing rules are unchanged. It reads three config keys read-only from the factory DB (same path rules as the goal lookup): `public_text_repos` and `frozen_repos` (comma-separated `OWNER/NAME`) and `scrub_terms_file`. Missing key = empty list. While both lists are empty the rule does nothing (no checker import, no git call), so private projects and the factory before cutover behave as before.

- **Commands in scope:** `git commit` (also `--amend`), `git tag -a/-m`, `git push` (every form), `git merge`; `gh pr create|edit|comment|review|close|merge`, `gh issue create|edit|comment|close`, `gh release create|edit`, and `gh api` with `-f/-F/--field/--raw-field/--input` or `-X POST|PATCH|PUT|DELETE`. They are found by the existing parser, so env prefixes, `sh -c`, chains and `$( )` are followed (in `--hq` mode the wrappers and `sh -c`/`eval` are followed by the rule itself).
- **Target repo:** `-R/--repo`, else the `gh api` path `repos/OWNER/NAME/...`, else `git remote get-url <remote>` (the named push remote, else `origin`) of the command's directory (`git -C` and `cd` are followed). A target that cannot be told is treated as public while `public_text_repos` is not empty.
- **Frozen rule:** target in `frozen_repos` -> `worker-guard: blocked (repo <slug> is frozen, G-021; work in the public repo)` for every command above, cleaner branch deletes included.
- **Public-text rule:** target in `public_text_repos` (or unknown). The text is the text flags of that one simple command (`-m/--message`, `--title/-t`, `--body/-b`, `--subject`, `--comment/-c`, `--notes/-n`, `-f/-F` field values), the files named by `--body-file/-F/--notes-file/--input` (unreadable -> blocked), and heredoc payloads (`--body-file - <<'EOF'`, `"$(cat <<'EOF' ... EOF)"`). Other commands in the chain (`cd <path> && git commit -m ok`) are not scanned. A body file (`--body-file/-F/--notes-file/--input`) is read when the hook runs, before the command does, so it is accepted only when the command is exactly that one `gh`/`git` call (no `;`, `&&`, `||`, `|`, `&`, `$(`, backtick, `<(`, `>(` or newline outside quotes; `2>&1` and `2>/dev/null` are fine) and the path is a regular file that is not a symlink and has one hard link; the real path's content is scanned. Anything else (a file written, checked out or rewritten in the same command) is blocked with "write the file in a separate command first". Dynamic text (`$VAR`, `$(cmd)`, backticks) is blocked with "write the text to a file and pass --body-file/-F". For `git push` every destination ref name is checked and so are the commits it would publish (messages, author/committer identities, paths, added lines) against the remote-tracking ref, or `git merge-base <src> origin/main` when there is none.
- **Terms:** `$SCRUB_TERMS_FILE`, else config `scrub_terms_file`. None readable -> `public-text-guard: no owner terms loaded`. The checker is `ci/public_text_guard.py` (see docs/public-text-guard.md), imported by path from the hook's own checkout; an import failure blocks when the rule applies.
- **Output:** exit 2 and `worker-guard: blocked (public text: <N> hits: <pattern ids>)`. The matched value is never printed.
- **HQ mode:** it allows on parse trouble everywhere else; for this rule only, a write command that cannot be parsed and targets a public repo is blocked.

Merge email (T-0602): the hook does not see merges that `factory judge` makes. The judge passes `--author-email <noreply>` and verifies the merge commit, and the tick alerts the boss about any non-noreply author/committer email on public `origin/main`; see docs/CUTOVER.md ("What the guards enforce").

Known limits: split or encoded terms (as in PUBLISHING.md); text produced by a program the command pipes in; a `$` in a flag value is treated as dynamic even if it was single-quoted (put the text in a file); wrappers such as `xargs` are not followed for text that arrives on stdin; `GIT_DIR=` env prefixes are not read (`--git-dir`, `-C` and `cd` are, and every directory a `cd` names counts, so a subshell cannot hide the repo); `git -c alias.*` is refused when the rule applies. Tests: `tests/test_worker_guard_public_text.py`.
